### Part 2: High-Concurrency Adaptive Engine & Load Shedding (FastAPI)
Create or update `backend/services/allocation_engine.py`:
- Compute Mode Toggle: Add an application-level state flag `COMPUTE_MODE = "NORMAL" | "THROTTLED_50"`.
- Fast-Path Ingestion (Decoupling):
  * When `COMPUTE_MODE == "THROTTLED_50"` and traffic spikes, the passenger intake endpoint `/api/passengers/submit` must NEVER run synchronous distance-matrix routing calculations.
  * Instead, do a lightweight write (`status="QUEUED"`) and return `202 Accepted` with `<50ms` latency.
- Algorithmic Downshifting:
  * In `NORMAL` mode: Run multi-factor weighted scoring with full pairwise distance calculations.
  * In `THROTTLED_50` mode: Downshift to an `O(N)` Geohash / Corridor Bucketing algorithm. Group passengers into predefined corridor buckets (e.g., `BUCKET_NORTH_TO_CENTRAL`) via a single hash-map lookup:
    ```python
    def corridor_hash(origin_lat, origin_lng, dest_lat, dest_lng):
        return f"{round(origin_lat, 2)}_{round(origin_lng, 2)}->{round(dest_lat, 2)}_{round(dest_lng, 2)}"
    ```
- Load Shedding:
  * Throttle WebSocket push frequency from 1s to 5s.
  * Use cached routing polylines rather than live external API calls.
  * Ring-fence compute solely for PostgreSQL/SQLite atomic seat reservation transactions (`SELECT ... FOR UPDATE` or serializable isolation) to guarantee an Over-Allocation rate of strictly 0%.
- Automatic Rollover: Any passenger unable to secure the 10 official seats immediately transitions to `status="CARPOOL_UNMET_DEMAND"` for community clustering.
